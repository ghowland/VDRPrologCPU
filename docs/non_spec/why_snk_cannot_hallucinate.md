# Why SNK Cannot Hallucinate: A Structural Analysis

## Background: How Conventional Language Models Fail

A large language model generates text by predicting the most probable next word from a vocabulary of tens of thousands of text tokens. The model learned these probabilities by training on trillions of words of human writing. Every fact, every reasoning pattern, every piece of knowledge the model possesses is encoded as statistical correlations between tokens — numerical weights distributed across billions of parameters.

When the model produces output, it samples from a probability distribution over its entire vocabulary at each step. The token it selects might correspond to a real fact retrieved from training data, or it might be a statistically plausible continuation that has no basis in reality. The model has no internal mechanism to distinguish between these two cases. Both are generated by the same process — predicting what text would probably come next based on patterns in training data.

This is what the field calls hallucination. The model states with full confidence that a function called `os.path.walkdir()` exists in Python's standard library. The output reads exactly like a correct answer. The function name follows real naming conventions. The description is technically coherent. But the function does not exist. The model assembled plausible-sounding components — a real module name, a realistic function name, an accurate description of what such a function would do — into a fabrication indistinguishable from a correct response.

The problem is architectural, not a matter of insufficient training data or inadequate fine-tuning. The model's output vocabulary consists of text fragments. Any combination of text fragments can be produced. Most combinations are meaningless, but the model's training biases it toward fluent, plausible combinations. Fluent and plausible are not the same as true. The model has no ground truth to check against because its knowledge exists only as weight patterns, not as addressable, verifiable facts.

## How SNK Is Structured Differently

SNK — Structured Neural Knowledge — is an architecture that separates knowledge storage from neural computation. Knowledge is stored as explicit, addressable facts in a hierarchical tree of knowledge bases. Each fact carries provenance — where it came from, how confident the system is, when it was recorded, and what rule or source produced it. Facts are connected by typed relations with known algebraic properties — some relations are transitive, some are symmetric, some have defined inverses.

The system includes a small neural network — approximately 143 million parameters organized in 6 transformer layers. This is roughly one-tenth the size of even modest conventional language models. The neural network exists to provide judgment at decision points where the mechanical systems cannot resolve a query on their own. At system maturity, approximately 93 percent of queries resolve without the neural network being involved at all, through direct traversal of typed relations between facts.

The critical architectural difference is in what the neural network predicts. A conventional language model predicts the next text token from a vocabulary of 32,000 to 128,000 text fragments. SNK's neural network predicts the next structural address from a vocabulary of 8,192 unique identifiers. Each identifier is a signed 64-bit integer that points to a specific entity in the knowledge base tree — a specific function, a specific concept, a specific operation, a specific knowledge base node. The identifier's bits encode its position in the tree, enabling direct navigation to the entity it references.

## Why Fabrication Is Structurally Impossible

In a conventional language model, the vocabulary contains all the building blocks needed to construct any English sentence, whether true or false. The text fragments "os", ".", "path", ".", "walkdir", "(", ")" are all valid tokens. The model can combine them freely. Nothing in the architecture prevents the combination, and the resulting output looks identical to a valid function reference.

In SNK, the vocabulary contains only identifiers that point to entities which exist in the knowledge base. There is no identifier for `os.path.walkdir` because that function was never recorded as a fact in any knowledge base, was never assigned an address, and therefore has no entry in the 8,192-identifier vocabulary. The neural network cannot predict an identifier that does not exist in its vocabulary, just as a person cannot dial a phone number that has no digits.

This is not a filtering mechanism applied after generation. It is not a safety layer that catches fabrications and suppresses them. The fabrication cannot occur in the first place because the vocabulary is a closed set of verified references. Every possible output of the neural network's forward pass — every single one of the 8,192 identifiers it could select — points to a real entity with real properties, real provenance, and real typed relations to other entities.

## What Errors Look Like Instead

The neural network can still make errors. When the probability distribution across the 8,192 identifiers is relatively flat — when multiple entities score similarly and the network has no strong basis for preferring one over another — it may select a suboptimal entity. It might select the identifier for `os.walk` when `os.listdir` would better serve the user's needs. Both are real Python functions. Both exist in the knowledge base with full documentation, typed relations, and provenance. Both would produce working code. The selection is suboptimal, not fabricated.

This error mode has three properties that fundamentally distinguish it from hallucination.

**The error is bounded.** The worst possible output is a real entity chosen for the wrong reasons. The entity has known properties, known capabilities, and known relationships. It is not an arbitrary fabrication — it is a real thing in the wrong place. The damage is limited to the difference between the selected entity and the optimal entity, not to the difference between reality and fiction.

**The error is detectable.** Every entity in the knowledge base has typed relations to other entities. When the neural network selects an entity, the system can mechanically verify whether that entity's typed relations cohere with the surrounding context. If the user's query requires a function that produces a list, and the selected function produces a dictionary, the typed relation `produces` does not connect to the expected type. The incoherence is a structural property of the knowledge graph, detectable by integer comparison, not by statistical judgment.

A conventional language model has no such verification mechanism. The fabricated function `os.path.walkdir()` has no typed relations because it does not exist in any knowledge base. There is nothing to check it against. The output token sequence is self-contained — it refers to nothing outside the model's weight parameters.

**The error is recoverable.** Because the suboptimal entity is real and has known properties, the system can present alternatives. It can identify the top-scoring candidates, show how each connects to the query context through typed relations, and let the user select. Or it can defer — reporting that no candidate connects well enough to proceed with confidence and requesting clarification. Recovery from a fabrication is impossible because there is nothing to recover to — the fabricated entity has no properties, no relations, no alternatives.

## The Completely Uncertain Case

Consider the worst scenario: the neural network's probability distribution is essentially uniform. All 8,192 identifiers score nearly identically. The network has no useful signal about which entity to select.

In a conventional language model, this scenario produces a random text token. That token might begin a fluent, plausible, entirely fabricated paragraph. The randomness is invisible to the user because the model's autoregressive generation means subsequent tokens are conditioned on the random first token, producing internally consistent but externally groundless text. The hallucination bootstraps itself into coherence.

In SNK, the same scenario produces a random identifier pointing to a random real entity. If the selected entity is from the wrong domain entirely — a chemistry concept when the user asked about programming — the typed relation check fails immediately. The chemistry concept has no `enables`, `requires`, or `produces` relations connecting it to the programming concepts in the resolved query context. The system detects the incoherence at the first relation check and rejects the selection.

If by coincidence the random selection happens to be from the right domain, the system checks the next relation in the chain, and the next, and the next. Each check is an integer comparison against a typed relation in the knowledge base. The probability of a random selection passing an entire chain of coherence checks decreases exponentially with chain length. A typical resolution requires three to seven coherence checks. The probability of a random entity passing all seven is negligible.

The result is that total uncertainty in the neural network produces an explicit failure — the system reports that it could not find a coherent resolution path and identifies where the chain broke. It does not produce confident-sounding output. It does not fabricate an explanation. It fails like a compiler encountering invalid syntax — precisely, at a specific point, with a specific reason.

## The Mechanical Path: No Neural Network, No Possible Error

Ninety-three percent of queries at system maturity never involve the neural network. They resolve through direct traversal of typed relations in the knowledge base. A query about what Python's `sorted` function accepts is resolved by walking the relation `sorted accepts iterable`, which is a fact in the knowledge base with provenance pointing to Python documentation at 80 percent confidence. The resolution is a series of integer comparisons against known facts. No probability distribution is consulted. No sampling occurs. No generation happens.

This path cannot produce any form of hallucination because there is no generative component involved. The system reads facts from the knowledge base and follows typed relations between them. If the fact exists, the system returns it with its provenance. If the fact does not exist, the system reports that it does not have the requested information. There is no mechanism for fabrication in a lookup operation, just as there is no mechanism for fabrication in a database query.

When the knowledge base has a gap — the user asks about a function that was never compacted into any knowledge base — the query returns no results. The system reports the gap explicitly, identifying which part of the query resolved successfully and where resolution failed. It does not generate a plausible-sounding substitute. It does not guess. It says what it knows and what it does not know, and the boundary between the two is exact.

## The Provenance Chain: Verifiable Output

Every fact in SNK carries a provenance record — the source type, the originating knowledge base, the confidence level, the timestamp, and the derivation rule if the fact was derived rather than directly asserted. When the system produces output, the user can trace every claim back through its provenance chain to the original source.

If the system states that `os.listdir` produces a list, the user can inspect the provenance and find that this fact was ingested from Python documentation at published confidence of 80 percent on a specific date. If the system derives a more complex claim through a chain of typed relations, every link in the chain is inspectable — which facts were used, what relations connected them, what confidence each carried, and what the overall chain confidence is, computed as the minimum confidence of any link.

A conventional language model cannot provide this. Its knowledge exists as distributed weight patterns with no individual addressable facts and no derivation chains. When asked to show its sources, it can only generate text that looks like citations — which may themselves be fabricated.

## Summary of Failure Modes

A conventional language model's failure mode is fabrication indistinguishable from correct output. The error is unbounded — the model can produce arbitrarily wrong claims with arbitrarily high apparent confidence. The error is undetectable from the output alone. The error is unrecoverable because the fabricated entity has no properties to check against or alternatives to fall back to.

SNK's failure mode is suboptimal selection from verified entities. The error is bounded — the worst case is a real entity in the wrong context. The error is detectable — typed relation coherence checks identify when a selection does not fit. The error is recoverable — the system can present alternatives, defer, or report exactly where resolution failed.

For 93 percent of queries, SNK has no failure mode at all. The mechanical resolution path reads facts and follows relations. It either finds the answer or reports that the answer is not in the knowledge base. There is no generation, no sampling, no probability distribution, and therefore no possibility of fabrication.

The distinction is architectural. It cannot be patched into a conventional language model through better training, larger datasets, or more sophisticated prompting. It arises from the fundamental design decision to separate knowledge storage from neural computation, to represent knowledge as addressable facts with typed relations rather than as undifferentiated weight patterns, and to constrain the neural network's output vocabulary to verified structural addresses rather than open-ended text fragments.
